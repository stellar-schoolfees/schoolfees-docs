## 3. Verified issues

Line numbers are from the files as they stand on 2026-10-01.

### CR-01 — A stale fee summary is shown after a successful write

- **Severity: medium**
- **Files:** `schoolfees-app/src/pages/PayPage.tsx:69-97` (`submit`),
  `schoolfees-app/src/pages/SchoolActionsPage.tsx:73-104` (`submitRefund`, `submitClose`)
- **What happens:** the page loads a fee once (`lookup`), renders `FeeSummary`,
  and then submits a write built from that captured record. After the transaction
  succeeds, the summary **above** the form still shows the pre-transaction totals,
  the panel is not marked as stale, and `PayPage` only ever prefills the amount
  once, at lookup time (`PayPage.tsx:64`).
- **Why it matters:** this is a financial UI. A payer who has just paid sees the
  full "Still owed" figure and can pay again; a school that has just refunded sees
  the old totals. Neither the app nor the contract treats the second action as a
  mistake (a duplicate `pay` simply succeeds, unless it overpays). It is also
  misleading in the plain sense.
- **Suggested fix:** after a successful write, re-read the fee with
  `client.getFee` / `client.getStatus` and update the summary, or (less good)
  label the summary in plain words as showing values from before the action. Keep
  a refresh failure from hiding the successful transaction hash.
- **Tracked as:** `schoolfees-app/docs/issue-drafts/10-refresh-fee-data-after-a-write.md`.
- **Status:** Fixed in `cf9fbe0` — `PayPage` and `SchoolActionsPage` now re-read the fee with `client.getFee` / `client.getStatus` after a successful payment, refund or close, so the summary updates to post-transaction values.

### CR-02 — `useAction.run` has no re-entry guard, so duplicate submission is only skin-deep

- **Severity: low** (medium impact if it triggers)
- **File:** `schoolfees-app/src/hooks/useAction.ts:18-38`
- **What happens:** `run` sets `busy` and awaits the task. Nothing rejects a
  second `run` while one is in flight — no in-flight ref, no generation counter.
  The only protection is that the submit buttons are disabled via the re-render
  that `setBusy(true)` triggers, plus `fieldset disabled={busy}`.
- **Why it matters:** the contract has no idempotency key, so a second `pay` is a
  second real payment. A second invocation is reachable from anything that is not
  the click path (a future keyboard shortcut, a retry wrapper, a bug in a
  component), and from a second browser tab, which has its own state. The guard is
  cheap; the failure is expensive.
- **Suggested fix:** keep an in-flight ref and/or generation counter inside
  `useAction` and ignore a second `run` while one is active; add a unit test that
  calls `run` twice with an overlapping promise and asserts the task ran once.
- **Tracked as:** `schoolfees-app/docs/issue-drafts/13-guard-against-duplicate-submission.md`.
- **Status:** Fixed in `d9c6b6c` — `useAction.run` now guards with a `busyRef` and a `generation` counter so a second call while one is in flight is dropped; a unit test asserts the task runs once.

### CR-03 — A read never keeps a fee record alive, because reads are simulations

- **Severity: low** (documentation accuracy plus a real, if distant, user-facing effect)
- **File:** `schoolfees-app/src/lib/contract.ts:131-145` (`read`), specifically the
  `simulateTransaction` call at `:133`
- **What happens:** `read` builds a transaction, simulates it, and returns the
  value. The transaction is never signed or submitted, so the TTL extension the
  contract performs while serving `get_fee` / `status` is **discarded**. Writes do
  go on-chain and do extend.
- **Why it matters, precisely:** the contracts repo documents the opposite
  expectation with its own caveat —
  `docs/design/interface-v0.md` §4: *"reads extend too, so `get_fee`/`status`
  submitted as transactions keep records alive (simulations do not persist
  extensions)"*. The docs repo's `limitations.md` and `threat-model.md` lean on
  "every read and write re-extends the entries it touches" as part of the archival
  mitigation. For anyone using the app, that protection does not apply. A fee
  nobody writes to can archive after roughly `due_at + 30 days`, and the app then
  shows its "archived, and this app cannot restore it" message.
- **Suggested fix:** choose explicitly — document the limitation for app reads
  (cheapest and honest), or have the app submit an extend transaction when it sees
  a record near the archival horizon (which depends on
  `schoolfees-contracts/docs/issue-drafts/07-extend-ttl-entrypoint.md` and costs
  the user a fee and a signature).
- **Tracked as:** `schoolfees-app/docs/issue-drafts/18-reads-do-not-keep-records-alive.md`.
- **Status:** Not fixed — documented as a limitation (draft 18). Reads remain simulations and do not persist TTL extensions.

### CR-04 — Dead export: `mapContractError`

- **Severity: low**
- **File:** `schoolfees-app/src/lib/contractErrors.ts:158`
- **What happens:** the module exports `mapContractError(error): string`, a
  wrapper around `describeContractError`. `grep -rn "mapContractError" src/`
  returns only its own definition — nothing calls it anywhere in `src/`, including
  tests.
- **Why it matters:** in a module whose entire purpose is to be the single trusted
  source of error wording, an unused half-featured helper is a trap: it drops the
  `nextAction` and `code` that `ErrorNotice` renders, so a future contributor
  reaching for it would silently degrade every error message.
- **Suggested fix:** delete it, or keep it deliberately with a comment and a test.
- **Tracked as:** `schoolfees-app/docs/issue-drafts/19-remove-unused-map-contract-error.md`.
- **Status:** Fixed in `1034b5b` — `mapContractError` was deleted; `grep -rn "mapContractError" src/` returns no references.

### CR-05 — The app's due-date check uses the device clock, not the ledger clock

- **Severity: informational — no action required**
- **File:** `schoolfees-app/src/pages/CreateFeePage.tsx:52-58`
- **What happens:** `nowSeconds = Math.floor(Date.now() / 1000)` is compared with
  the parsed due date, and the message shown is the `DueDateInPast` wording. The
  contract compares `due_at` against `env.ledger().timestamp()`.
- **Assessment:** this is a *pre-check for the user's benefit*, not a rule. The
  contract remains authoritative, and a device clock that is wrong in either
  direction produces at worst a rejection carrying the contract's own reviewed
  wording, or an unnecessary round trip. Dependency-injecting a clock so the check
  can be unit tested would be nice, not necessary. Recorded so that it is not
  mistaken for a bug, and so nobody "fixes" it by trusting the client clock.
- **Not drafted**, deliberately: it is not a defect.
- **Status:** Not fixed (informational, intentional) — the device-clock pre-check remains as described; it is a user-facing hint, not a rule.

## 4. What was checked and found clean

Verified positively, so the absence of findings above is evidence rather than an
omission:

- **Contract module boundaries hold.** `src/lib.rs` contains only
  `#[contract]`/`#[contractimpl]` and one-line delegations; logic, storage and
  validation live in `src/fee.rs`; types, errors and events in `src/types.rs`;
  keys and TTL helpers in `src/storage.rs`. No storage key is constructed outside
  `src/storage.rs`; no business rule lives in `lib.rs`.
- **The app's contract calls match the contract exactly**, name for name and
  argument order for argument order (`create_fee`, `pay`, `close_fee`, `refund`,
  `get_fee`, `status`), and the ScVal conversion round-trips against the real SDK
  encoders in tests.
- **Money is never a JS `number`.** Amounts are `bigint` end to end; the contract
  uses `i128` with checked adds and a release profile that traps on overflow.
- **No loops or unbounded inputs in the contract**; every lookup is keyed.
- **`src/config.ts` is the only place the environment is read**, and the app never
  sees a raw env value or an `any`.
- **No `any`, no `as`, no non-null assertion** found in `src/` (the only `any`
  matches are `overflow-wrap: anywhere` in CSS).
- **Strict TypeScript, no inline styles, no CSS-in-JS, no framework CSS** — one
  stylesheet, tokens in `:root`.
- **Components hold no business logic**: every rule the UI enforces
  (`validate*`, `parsePositiveAmount`, `remaining`, `canClose`, `describeStatus`,
  `describeContractError`) is a pure, unit-tested function in `src/lib/`.
- **No dead scaffolding**: no Vite/React starter files, no `src/assets/`, no
  commented-out blocks, no TODOs other than the one documented `TODO(verify)` at
  `src/lib/contractErrors.ts:143`, which is already an open item in
  `src/todo-verify.md`.
- **Comments explain why, not what** throughout, including the deliberate panics
  in `src/fee.rs::add` (checked add that traps) and the fee-id counter.
